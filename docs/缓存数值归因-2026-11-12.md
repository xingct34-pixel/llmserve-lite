# CPU前缀缓存数值归因（2026-11-12）

本轮针对上次“共享前缀请求后段文本不一致”的具体样例建立4路原生对照，使用同一份固定Q4_K_M权重、CPU2线程、context512、n_batch128、n_ubatch64，16步均强制喂入全量基线选择的同一token，比较完整logits向量，而不是仅看文本非空。

## 对照与结果

1. B整段Prefill：全量基线。
2. B先算共同前缀9 token，再算后缀：没有跨请求复用，只改变分块方式。
3. A完成Prefill后裁去共同前缀外的KV，再算B后缀：当前缓存路径。
4. 与A计算批大小相同、共同前缀相同的因果参考，再裁剪并计算B后缀：控制计算形状。

无跨请求缓存的分块路径也产生数值差异，并在16步中出现1次argmax不同；缓存路径同样出现1次。缓存路径与相同计算形状的因果参考在全部对照步的最大logits误差为0。首步全量与缓存的max_abs约0.40958、KL约0.00665；这些不是“逐位等价”的结果。

这些实验支持本例差异与上游量化CPU分批计算路径的数值变化有关，不能仅因生成文字不同就认定旧请求KV串入。它也不证明所有模型、输入、硬件和版本均不存在状态错误，或完整定位到某一具体底层kernel。现有取消/异常后的全量恢复测试继续严格检查隔离基线。

## 使用边界

prefix_cache_tokens仍默认0关闭；要求严格逐字复现时保持关闭。新增诊断不改变在线推理算法，不把测试通过描述为所有缓存文本完全一致，也不把单例Prefill减少当成稳定加速倍数。多租户缓存、持续会话和连续批处理仍未实现。

```bash
cmake --build build/cpu --target prefix_numeric_probe -j2
build/cpu/prefix_numeric_probe models/qwen2.5-0.5b-instruct-q4_k_m.gguf
```

CPU CTest在本地模型存在时包含real_prefix_numerics；没有模型时不隐式下载。机器可读完整16步结果见docs/benchmarks/prefix-numerics-2026-11-12.json，原始日志在results/2026-11-12-finalization。
