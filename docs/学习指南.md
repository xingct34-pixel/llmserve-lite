# 从一次请求理解服务

按 `src/main.cpp → Scheduler::submit → Scheduler::run → Engine::generate → Job::emit/next → SSE provider` 阅读，再看 tests/core_tests.cpp、tests/integration.py 和真实测量脚本。

## 所有权

Scheduler 独占 Engine，worker 使用同一个模型和 context；Job 通过 shared_ptr 在 handler、worker、stream 间存活。调度器锁保护队列和计数，Job 锁保护事件缓冲与终态。cancelled 为跨线程原子标志。worker 推理时不持有调度器锁。

## 请求生命周期

接入校验 → 在途限额 → 有界等待队列 → worker 开始 → 格式化与分词 → 分块 prefill → 逐 token decode → UTF-8 拼接 → 有界输出缓冲 → HTTP 写入 → 终态。

终态不占 delta 缓冲，避免慢客户端使结束消息永远无法入队。取消是协作式，不能保证在任意底层调用中立即中断。SSE 首段发出后 HTTP 状态不能再改，中途错误由流内 error 事件表达。

## 指标的边界

Scheduler completed 是生成成功，不证明客户端完整接收。http_status_429 等计数来自 HTTP 库响应日志，包含已记录的接入层拒绝，但不覆盖未形成有效 HTTP 响应的底层连接失败。压测以客户端观测为准。SSE 中途 error 可以仍对应 HTTP 200。

first_token_ms 从 worker 开始到首个完整 UTF-8 delta 入缓冲，不含排队和网络传输；客户端 TTFT 包含这些开销。token 数和 SSE delta 数不同，中文 token 可能只包含一个字符的部分字节。

## 建议亲自完成的练习

1. 画出模型、context、Job 的销毁顺序。
2. 独立实现有界队列，解释每把锁和等待谓词。
3. 改变队列容量，预测拒绝率和尾延迟再实测。
4. 制造推理异常、慢消费者和断连，观察下一请求能否成功。
5. 分开测 prefill/decode，解释线程数增加不一定更快。

本项目没有实现 continuous batching、跨请求 KV 复用、多 GPU 或分布式调度。学习这些机制时，应先理解目前单 worker 的局限，再对照主流框架。
